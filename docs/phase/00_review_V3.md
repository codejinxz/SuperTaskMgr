## 二、P0 缺口（必须补）

### P0-1 已确认产品决策"1A 单进程模型（默认普通权限，一键重启提权）"无任何技术落点与验证项

主报告首页已确认该决策，但**通篇（含 R5/R6 与 §8 待验证清单）没有任何一处回答"一键提权重启怎么做"**。具体缺失：

1. **提权重启实现**：ShellExecuteExW + lpVerb="runas"（文档化 Shell API）+ exe 内嵌 manifest requestedExecutionLevel=asInvoker + 用户取消 UAC 时 ERROR_CANCELLED 的处理。主报告/R5 未提。
2. **单实例互斥**：命名互斥（CreateMutexW）+ ERROR_ALREADY_EXISTS 激活既有窗口；与"重启提权"叠加后的**交替竞态**——新提权实例启动时旧普通实例尚未退出，互斥体持有顺序、等待/握手事件（旧实例收到通知→放互斥→退出→新实例接管）必须设计，否则提权重启必然撞单实例。
3. **1A 状态传递**：提权重启后恢复现场（当前页面、选中进程 (PID,CreateTime)、窗口位置、过滤器），需定义进程命令行参数或临时文件的传递协议；被选中进程若在重启窗口期退出，按身份规则静默降级。
4. **功能×权限矩阵缺失**：1A 模型下哪些功能普通权限可用、哪些降级、哪些必须提权重启——R5 备注1 有素材（ETW、服务启停、HKLM StartupApproved、计划任务系统文件夹、SMART/MSAcpi、清待机列表、24H2 驱动枚举、跨会话查询），但主报告未固化成矩阵。该矩阵是阶段 2 UI 交互（降级提示 vs "提权重启"按钮）与验收的直接依据。

**修正建议**：① §8 待验证清单增补"提权重启链路端到端验证"（runas→UAC 取消→互斥交替→状态恢复，含普通权限杀 lsass 属主进程失败→提权重启后成功的实测）；② 阶段 1 架构文档增设"进程模型与提权"专节（互斥/握手/参数协议/manifest）；③ 权限×功能矩阵作为架构文档必选章节；④ 阶段 2 验收将"提权重启→杀原杀不了的进程"列为必测项。

## 三、vcpkg → vendoring 论证评估

**结论：决策正确、论证基本成立，但需补强成正式决策记录（P2-3）。**

成立的部分：本机 vcpkg/pip/python 均不可用（主报告§9 实测）；vcpkg 编 Qt 成本 1-2h/30GB（R1 实引讨论区）；imgui/implot 源码 vendoring 约 2MB、离线可复现、双 MIT（R2§7 给出了无 vcpkg 的完整获取路径：tag tarball 一次性下载 → CMake add_library）。原始约束是"CMake+vcpkg/MSVC **建议**"，CMake+MSVC 均保留，仅替换依赖获取方式，未违背约束精神。

需补强的部分：主报告只在 §4.2/§9 顺带提及，**没有一处正面回答"为什么不用 vcpkg"**。建议架构文档"构建系统"一节补：① 决策记录（上述三条依据）；② imgui/implot tag 锁定与升级流程（§7 风险1 已有原则，需落到操作步骤）；③ FreeType 若从"可选"转正，走官方 tarball vendoring + FTL 许可文本入库（R2§7 路径），**不引入 vcpkg**——即 vcpkg 不作为任何组件（含 FreeType）的获取通道，保持零外部包管理器依赖；④ vendoring 代码与本项目代码的目录隔离与"不得修改第三方源码"纪律（补丁以 patch 文件形式维护）。

## 四、待验证清单排雷能力评估

**现有清单质量高**：R5 表B 14 项覆盖了采集层两大真雷区（NtQSI 偏移交叉验证、PDH 通配符/陈旧实例）与启动项三个未文档化写入（StartupApproved/UWP State/put_Enabled），裁决方法具体可操作。

**漏掉的高风险项**：
1. 提权重启链路（→ P0-1，最大漏项）；
2. GPU 虚拟适配器过滤（→ P1-5）：主报告§9 已实测本机存在两块虚拟显示适配器并要求"采集层需过滤"，但**如何过滤**（DXGI EnumAdapters1 + LUID 与 PDH 实例对齐、虚拟适配器判定依据）既无落点也无验证项——不验证则 GPU 页在大量机器上会出现重复/幽灵适配器数据；
3. R6 自身标注的待验证项未全量登记进 §8（→ P2-4）：MSAcpi 管理员下是否返回有效值、nvml.dll 随应用再分发的 EULA 条款、igcl64.dll 实际安装位置（DriverStore?）、SATA SMART 0 权限句柄纯查询可行性；
4. WinVerifyTrust 批量冷启动开销（500 进程首次全量校验为 ms 级×N，缓存策略已有但冷启动体验未量化）（→ P2-4 合并验证）。

结论：**补入 P0-1 与 P1-5 后，清单才足以支撑阶段 1 排雷**；否则阶段 2 中后期才会在提权链路与 GPU 页返工。

- **Build**：CMake 生成 + MSVC /W4 零警告；Release 单 exe，体积实测记录（预期 ≤5MB 量级，超出需说明）；
- **冒烟自测（可脚本化）**：冷启动 ≤2s；进程数与任务管理器一致（±System/Idle 等口径差说明）；抽 10 进程 CPU/内存/路径与任务管理器比对在口径误差内；500+ 进程下 UI 帧时间 <8ms（目标 ≥55fps）；采集线程自身 CPU <2%；1Hz 连续运行 10 分钟无内存增长趋势；
- **手工验收清单**：① 结束普通进程成功；② 树杀 cmd→ping 树成功；③ 结束 System/lsass 被保护名单拦截且有提示；④ 一切终止操作出现二次确认；⑤ 提权重启（含 UAC 取消路径）后可终止普通权限下 ACCESS_DENIED 的进程，且重启后恢复原页面/选中项；⑥ 从含中文+空格目录启动测试进程，路径/命令行显示正确；⑦ 禁用独显/无 GPU Engine 计数器机器（或 WARP）不崩溃；⑧ 断网/无网络计数器场景正常；
- **演示脚本**：5 分钟固定路径（含一次提权重启、一次树杀、一次保护名单拦截）。

### 阶段 3（扩展功能）
- 启动项：四源枚举与任务管理器"启动应用"数量一致（±已知差异清单）；禁用一条 HKCU 启动项后任务管理器开关状态正确显示；计划任务禁用一条自建任务后 schtasks 查询确认；
- 服务：启停一个无害服务成功且依赖服务先停；驱动列表条数与 `driverquery` 一致；
- 网络：TCP/UDP 表与 `netstat -ano` 抽样 20 条完全一致；提权后按进程流量页有数据且与任务管理器量级一致；
- 传感器：本机可达项全显示、不可达项显示"需要驱动支持"字样（**不得出现假数据或 0 占位**）；SMART 与 CrystalDiskInfo（如可装）量级一致；
- 悬浮窗/告警（若纳入 MVP）：各一条手工用例（悬浮窗置顶/拖拽/隐藏；告警阈值触发托盘通知）。

### 阶段 4（打磨 + 发布）
- 24h 挂机：PrivateUsage 增长 <10MB、采集线程平均 CPU <1%；期间无崩溃/无 WER 事件；
- 干净环境冒烟：干净 Win11 虚拟机（及 24H2，如可得）仅拷贝便携目录即可运行；24H2 驱动列表降级提示按矩阵出现；

- 中文路径全功能回归用例通过（含中文启动项名、中文服务路径、中文计划任务名）。

## 八、总体结论

选型结论本身**支撑原始需求**：45 个核查点中 96% 有落点或有限制已诚实声明，唯一完全无落点的"告警"属 ⑧ 的开放范围项。采集层研究（R5/R6）质量显著高于 UI 层研究被引用的粒度——主报告 §5 基线表忠实继承了 R5/R6 的成果，但**在"已确认产品决策（1A 提权模型）→ 技术落点"的映射上出现断层（P0-1）**，且任务管理器对等指标（GDI/USER、Elevated、Hard Faults）与阶段计划/验收两层内容缺失。补 1 项 P0、7 项 P1 后，阶段 1 即具备写出完整架构文档的全部输入；本审查第五、六节建议稿可被架构文档直接采用。
