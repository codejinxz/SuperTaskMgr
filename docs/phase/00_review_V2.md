## 发现列表

### P1-01 采集层基线表（§5）系统性遗漏，作为"直接进入阶段 1"的输入不完整
**问题**：对照任务管理器级功能基线，§5 至少缺以下条目（API 均已查证可达）：
- GDI/USER 对象数：`GetGuiResources`（GR_GDIOBJECTS/GR_USEROBJECTS，QLI 权限，每进程 2 调用）——"超级任务管理器"排查 GDI 泄漏的标志性功能，R5/主报告均无
- 窗口标题/未响应标记：`EnumWindows`+`GetWindowThreadProcessId`+`IsHungAppWindow`（"应用程序"视图与"未响应"标注的基础）
- 命令行：`NtQueryInformationProcess(ProcessCommandLineInformation)`（半文档化，QLI 即可，PPL 除外，须阶段 1 验证）
- 提权标记与属主用户/会话：`OpenProcessToken`+`TokenElevation/TokenUser/TokenSessionId`（或 WTSEnumerateProcesses）
- 每进程缺页：`GetProcessMemoryInfo.PageFaultCount`（累计增量）+ PDH `\Process(*)\Page Faults/sec`（软+硬合计）；纯硬错误无文档化每进程计数器（系统级 `\Memory\Pages Input/sec`），口径须如实标注
- 上下文切换：NtQSI 线程级 ContextSwitches 汇总（半文档化字段）或 PDH `\System\Context Switches/sec`
- 每核 CPU：PDH `Processor Information(*)\% Processor Time`——R5#15 有，主表未落
- GPU 适配器级显存/总显存：`\GPU Adapter Memory(*)\Dedicated Usage` + `DXGI_ADAPTER_DESC.DedicatedVideoMemory`
- 每进程模块列表：`EnumProcessModules`（需 QUERY+VM_READ，他人进程需提权）
- 另：R5 已调研的**服务管理/启动项/驱动列表**三块未落入 §5；§9 实测发现的"两块虚拟显示适配器需过滤"也未写入 §5 GPU 行
**影响**：阶段 1 按此开工必然中期返工；GDI 句柄数、未响应窗口、硬错误等恰是本产品区别于原版任务管理器的卖点，漏掉等于放弃定位。根因是主报告没有"产品功能清单/验收范围"章节，§5 只能是 R5 的无标尺子集。
**建议**：报告开头补一节功能范围清单（P0/P1/P2 需求分层）；§5 按 R5 格式增补上述 10~12 行（权限/对策/验证项齐全）；服务/启动项/驱动行按范围取舍后搬入。

### P1-02 "Toolhelp 全功能兜底"表述失实，NtQSI 风险对冲须改为可执行降级链
**问题**：R5#1b 自己写明 Toolhelp 仅 PID/父PID/线程数/EXE 名，**无 CPU/IO/句柄数**，快照非原子一致；主报告 §7.2 却写"Toolhelp 全功能兜底开关"。纯 Toolhelp 兜底 = 降级为"进程列表模式"，不是全功能。
**影响**：风险缓解条目按字面不可执行；一旦 NtQSI 偏移在某个目标机失效，实际行为是功能大面积缺失，而报告承诺的是"全功能兜底"。
**建议**：§7.2 改为三层降级链：① NtQSI 快路径；② **启动时自校验门**——用 NtQSI 读自身 PID 的 CPU/内存值与 GetProcessTimes/GetProcessMemoryInfo 交叉比对，误差超阈值即本次会话自动走③（这是对"半文档化"最廉价、最有效的运行时对冲）；③ Toolhelp 枚举 + 每进程 OpenProcess(QLI) + GetProcessTimes/GetProcessMemoryInfo/GetProcessIoCounters 逐进程采集（全文档化慢路径，800 进程×每秒可行），UI 标注"兼容模式"。IO 字段交叉验证对象补上 GetProcessIoCounters（§5 只写了 Times/MemoryInfo）。

### P1-03 结论与风险条目自相矛盾：docking 依赖 WIP 分支，"固定稳定版+锁定 tag"缓解无法按字面执行
**问题**：结论行写"Dear ImGui（docking 能力所依赖的最新稳定版）"，§7.1 写"固定 vendoring 版本、锁定 tag"。但 R2§1 查证：docking 至今未入主线，docking 能力只存在于 1.93.0-WIP 分支，**不存在含 docking 的"稳定版"**。产品核心（多面板停靠、悬浮传感器窗）压在一个无正式发布 tag 语义的分支上，而缓解文字假设存在稳定版。本次独立检索证实其风险实际可控（官方推荐、大量商业项目生产使用、持续同步），但文档必须与事实一致。
**影响**：阶段 1 若按字面"锁定稳定版 tag"操作，会丢失产品赖以成立的停靠/多视口能力；或临时改用 WIP 分支而绕过升级评审流程。
**建议**：依赖表明确锁定一个 docking tag（如 vX.Y.Z-docking）或 commit hash；§7.1 改写为"docking 为维护中分支，锁定 tag，升级走显式评审"；增加"无停靠回退"编译开关（单窗布局）保证分支异常时产品仍可用；README 声明使用 docking 分支。

### P1-04 定位自洽性与评分敏感度缺失；"UI能力"维度未区分真正的差异轴
**问题**：①矩阵中 Qt 与 ImGui 在"UI能力与体验(20)"同为 4 分：Qt 具备原生观感/IME/HiDPI/无障碍/暗色开箱即用，ImGui 全部缺失，两者却同分——评分轴未区分化，把两路线最大差异轴隐藏在矩阵之外。ImGui"长期维护 4"亦未扣 docking WIP、单一核心维护者、1.92 大改版、implot 换任的分。②更深一层是**定位漂移**：用"管理员自用"论证牺牲无障碍（§三），又用"便携分发最小体积"论证否决 Qt（§四.4）——若纯自用，Qt 的 60MB 无关紧要而其无障碍/成熟控件全是净收益；若真分发，未签名管理工具的 AV/SmartScreen 风险与 UIA 缺失影响远比报告承认的大。两组论据各取所需。
**影响**：反方复核下优势从 0.55 缩到约 0.35（UI能力 ImGui 3.5/Qt 4.5、维护 3 → ImGui≈4.55~4.65 vs Qt 4.30），决策仍成立但报告未呈现稳健性论证，可信度受损。
**建议**：①开头写死产品定位（自用/小圈子/公开分发）并让权重与论据一致；②矩阵为无障碍设独立维度或在 UI 能力栏写明扣分明细；③补一句敏感度结论："即便 UI/维护维度下调，ImGui 仍领先 Qt 0.3 以上，决策不翻"。备注：#8022 显示 1.92.x 已有无障碍地基工作，长期看 ImGui 最大的劣势有缩小可能，可列为跟踪项而非永久定论。

### P1-05 Qt 否决中"构建现实"论据失真（虚假约束入论证链）
**问题**：§四.2 与 §三 以"pip/python 不可用 → aqtinstall 路径断裂"作为 Qt 否决论据。不成立：aqtinstall 本质是 URL 拼装下载器，官方归档（qtsdkrepository）的 .7z 包可用 Git 自带 curl 直接下载解压；便携版 Python embeddable zip 免安装免管理员；TUNA 镜像可用（R1 自己已写明）。vcpkg 同理是"成本高（1-2h/30GB，此数据诚实）"而非"路径断裂/不可用"。
**影响**：一条虚假约束进入仲裁依据，会连带削弱全部"构建现实"论证的可信度。Qt 的体积/内存/许可劣势独立成立，结论不翻，但论证链必须去污。
**建议**：§四.2 改写为"Qt 获取可行但成本高（1GB 级下载、装后 2.5~3GB、开源 LTS 补丁窗口止于 6.8.3），且 50-80MB 分发与 30-60MB 空载内存同最小便携定位冲突"，删除"路径断裂"表述。

### P1-06 合规与透明声明缺失：既定约束（仅本机系统管理、无隐蔽/持久化/规避）未落到工程条目
**问题**：全文除 a11y 外无任何透明性/合规设计条目。具体缺口：
1. **未签名管理工具**（终止进程+写自启动注册表+停服务+ETW 内核会话）是启发式误报与 SmartScreen 拦截的重灾区，签名策略零字提及；
2. WinVerifyTrust 吊销检查默认会发起网络访问，与"无网络工具"姿态冲突，需默认 `WTD_REVOCATION_NONE`/`CACHE_ONLY`（R5 提到"控制吊销网络"但未成为设计规则）；
3. ETW 内核会话生命周期未定：命名规范、随进程退出清理、崩溃后下次启动清理残留、`logman query -ets` 可见可停——正当且透明即可，但要写成规则；
4. "本工具自身不持久化"（不写自身自启动、不装服务、不留计划任务）应升级为硬性设计规则，与"不得含持久化能力"约束对齐；
5. 启动项禁用是对第三方软件的管理操作：StartupApproved/计划任务为社区逆向格式，**写入前备份原值、UI 一键还原、操作留痕**，做到可逆可审计。
SeDebugPrivilege（终止/24H2 驱动枚举）与 ETW 的用途本身正当（与任务管理器同型），无踩线设计；问题只在"透明"未工程化。
**影响**：约束只停留在决策语句，阶段 1 无法验收；分发时首台陌生机器即可能被 SmartScreen/AV 拦截。
**建议**：§7 后新增"合规与透明"一节，并落实下述 README 声明清单（附录）；发布形态定为"签名单 exe + SHA-256 校验和"，无法签名则 README 明示绕过步骤与哈希。

### P1-07 传感器模块对外承诺需收紧（三处夸大、一处漏项、一处许可陷阱）
**问题**：
1. §5 把 `MSAcpi_ThermalZoneTemperature` 标为"CPU 整包温度"——R6 已查证它是 ACPI 热区（板级、每板 1~2 个 zone、消费级台式机常缺失/恒值），当"CPU 温度"显示即违背"绝不显示假数据"的自我承诺；UI 标签应为"ACPI 热区温度"。
2. R6 矩阵 GPU 温度"各自全"对 Intel 过乐观：IGCL 温度取决于驱动版本；`igcl64.dll` 实际安装位置（DriverStore）发现路径未解；本机管理员下 MSAcpi 取值有效性"待验证"——**§8 移交清单漏了这条**（只移交了 IGCL 头文件/NVMe/ATA 三项）。
3. SMART"全"应限定"内置/直连盘"；USB 桥取决于桥接芯片 SAT 支持（R6 旁证 CrystalDiskInfo 多路径，主表未带限定）。
4. "风扇用户态不可达"应补 OEM 例外（部分 OEM 有私有 WMI/EC 接口），避免结论被个案推翻；主线结论维持。
5. **许可陷阱**：IGCL 头文件为 Intel EULA（仅限 Intel 平台、GitHub license=Other），不得随 MIT 项目/仓库分发；NVML/ADLX 头文件同理有厂商许可约束。主报告§六依赖表完全未列厂商 SDK 头文件。
**建议**：§5 传感器行按上述改写；§8 补"MSAcpi 管理员取值有效性（对照 HWiNFO 读数）"；厂商 SDK 一律运行时动态加载系统已有 DLL + 自声明最小原型，**头文件不入库不入包**，README 许可节写明。

### P2-08 选项空间缺口：两条中间路线未评估即被隐式否决
纯 Win32 原生控件（ListView 虚拟化+自绘图表）仅在 R2 一句带过（LVM_* 封送慢），无独立评分；它是原版任务管理器的技术路线，具备原生观感与部分 a11y。"C+++WebView2"（去 Rust 的 Tauri 变体）可 100% 复用 C++ 采集层、MIT、Win11 预装运行时，R4 只评了 Tauri。两者大概率仍被否决（消息封送/自绘工作量 vs IPC 协议+40-150MB 渲染进程），但应留书面否决记录。**建议**：§三 末补"已考虑并否决的中间路线"小节，各 2~3 行理由。

### P2-09 "UI 层整体替换"逃生舱成本被低估；implot 降级方案未上主报告
"UI 层整体替换、采集层原样复用"架构成立，但实际含义是**全部 UI 代码重写（数周~数月）**，非换库；立即模式下 UI 代码与展示逻辑天然交织，边界只在数据接口。R2§⑤ 为 implot 设计的"薄封装+必要时自绘折线"降级方案未进入主报告。**建议**：现在即定义 UI/采集层纯 C++ 数据接口头；Qt 备选条目注明切换成本估算；主报告补 implot 薄封装规则与自绘降级。

### P2-10 立即模式"无小事"清单应精确化：既有真实负担，也有被高估的项
真实自建项：单元格富文本/行内迷你图（ImDrawList 手拼）、表格行复制/导出、跨面板拖放、键盘导航细节、系统明暗主题跟随（自管颜色表+`DWMWA_USE_IMMERSIVE_DARK_MODE`）、托盘 `TaskbarCreated` 重挂、`IFileOpenDialog` 模态期间渲染循环暂停/重入、IME 合成窗定位（多视口更甚）、WARP（RDP/虚拟机）下 60fps 全量重绘预算（建议检测 WARP 后限帧/减列）。**被高估项（内建，不必手写）**：列宽拖拽、列可见性、排序、窗口位置持久化均由 ImGui Table settings/imgui.ini 原生支持。建议劣势清单分"内建/自建"两栏，避免阶段 1 重复造轮子或漏估。

### P2-11 字体决策两份文件矛盾，且无回退链
R2§3 明确"推荐 FreeType（质量优先）"，主报告§六降为"可选升级"。本工具是小字号大表格形态，stb 无 hinting 的 CJK 发糊是真实风险。msyh.ttc 缺失/更名场景（精简系统）无回退。**建议**：阶段 1 做 30 分钟 spike（12/14/18px 中文 stb vs FreeType 同屏对比）后定案；写明回退链 msyh.ttc→simsun.ttc→纯英文 UI。

### P2-12 关键进程保护名单与 R5 不一致；透明性可再增强
主报告§5 名单（System/Idle/smss/csrss/wininit/winlogon/services/lsass/Registry/Memory Compression）比 R5#7d **少了 dwm**（R5 明确列入）。**建议**：名单以 R5#7d 为准对齐；名单外高危目标（dwm、svchost 内服务）加二次确认 + UI 操作历史（审计日志），是"透明"约束的落地形式。

### P2-13 vendoring 单点风险整体可控，但退出策略要写全
先说结论：MIT+源码 vendoring 意味着即使上游消失，项目可无限期在本地副本演进——**退出成本为所有候选 UI 方案中最低**，这一点论证扎实。残余风险：安全修复跟踪节奏、docking 分支独有缺陷可能永无 tag 化修复、implot 换任后响应变慢（R2 有缓解措施、主报告未收录）。**建议**：依赖表加"升级评审触发条件"（安全公告/阻塞 bug/主线合并 docking 事件）；冻结 tag 时记录 commit hash 与 tarball 哈希——主报告宣称"离线可复现构建"，记录哈希是该承诺的最后一环。

## 论证扎实的方面

- **矩阵算术与否决证据链**：五路线加权分逐格复核无误；WinUI3（CMake 官方不可行、无 C++ DataGrid、MSIX 提权崩溃）与 Tauri（sysinfo 约半数采集缺口、三栈调试成本）否决证据可独立复核，无过重之嫌。
- **WinRing0 判死**：官方 Recommended_Driver_Blocklist.xml 29 条 Deny 实证 + "方案B 仅文档化不随包分发"，是全部材料中合规最强的决策；PawnIO 迁移趋势判断与行业一致。
- **诚实性文化**：拿不到的数据显示"需要驱动支持"而非假数据；PDH IO 口径含网络的如实标注；MemoryPurgeStandbyList 局限、OWNER_MODULE 非管理员为空、非管理员降级路径均如实。
- **采集层工程判断成熟**：(PID, CreateTime) 进程身份、PdhAddEnglishCounterW 本地化对策与通配符展开、PPL 天然防误杀、SeDebugPrivilege 最小化使用、关键进程名单。
- **本机实测使论据脱离纸面**：PDH 11 条、CallNtPowerInformation、MSAcpi 非管理员被拒、netstat -ano、VBS/HVCI/SAC 状态，且明确声明"不可假设目标机同样配置"。
- **流程本身是完备性对冲**：6 独立调研 + 3 独立审查 + 本轮反方评审，决策非单人拍板。
